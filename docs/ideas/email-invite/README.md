# 構想：預約時寄 Outlook 會議邀請給與會者

狀態：構想（未決），2026-11-02 整理。來源：同事建議「既然能設定到人員名稱，就能對到 Mail，預約時寄會議通知到與會者信箱，可設 Outlook 提醒」，同一則訊息也提議把系統搬到內部 VM 架設。

**已定方向（使用者 2026-11-02，決策紀錄 D-2）**：寄法採 B（後端用系統信箱寄邀請信）；順序是**先把系統搬到內部 VM，再做寄信**，寄信後端放在 VM 上。細節見下方「B 在 VM 上的做法」。

## 目標

預約時，讓與會者在 Outlook 收到正式會議邀請：可以接受或拒絕，會進行事曆，會跳提醒。信箱一律是 `{帳號}@gamasys.com.tw`。

## 現況（2026-11-02 實查）

- 與會者選單的名單寫死在 `index.html` 的 `attendeeGroups`／`ATTENDEE_TEAMS`，存的是暱稱（例：`Faust`、`Ryan`、`小威`），以文字存進 `bookings.attendees`；名單外人員可手動輸入。
- 「加入行事曆」產生的 `.ics` 是 `METHOD:PUBLISH`，只加進自己的行事曆，不寄給任何人。
- 公司分機表（`\\10.10.2.5\共用區\公告\00.分機表+位置圖\gama 分機表.xlsx`）有「姓名」「Mail」欄，Mail 只存帳號前綴，約 38 人。

## 關鍵限制

- 要寄出正式邀請一定要有後端代寄；目前系統是純前端（GitHub Pages＋Supabase）。後端可以放內部 VM，也可以放 Supabase Edge Function（2026-11-02 選前者，先搬 VM，見上方）。
- 暱稱和信箱帳號不是一對一可推導（例：`Faust` → `faustguo`），要建「暱稱 → 帳號」對照表，由使用者逐一確認；名單外人員沒有信箱，不寄。
- 對照表不能放進公開的 `index.html`（GitHub Pages 公開），否則等於公開全公司信箱名單。

## 寄法比較

| 做法 | 收件者看到什麼 | 需要什麼 | 評估 |
|---|---|---|---|
| A. 只改前端（`.ics` 或 `mailto:` 帶好收件人） | 普通信件，或要自己手動轉成會議 | 不需要後端 | 半自動，只能當過渡 |
| B. 後端用系統信箱寄 iCalendar 邀請（`METHOD:REQUEST`）（已選，D-2） | 正式 Outlook 會議邀請 | 系統寄件帳號或 SMTP relay，加一個小後端 | 成本適中，跟 VM 方案最搭 |
| C. Microsoft Graph 寫進預約者的 Outlook | 跟在 Outlook 自己開會議一樣 | 公司是 M365，IT 在 Azure 註冊應用程式並給權限 | 最原生，要 IT 配合最多 |

B 的主辦人用系統信箱（例：`meeting-room@gamasys.com.tw`），預約者也列為與會者；接受／拒絕的回覆會寄到系統信箱，不會寄到預約者那裡。

## B 在 VM 上的做法（2026-11-02 定案方向）

- 前置：系統先搬到內部 VM（另一件工作，範圍待定：只搬網站，還是連 Supabase 資料庫一起搬）。寄信等搬完再做。
- 寄信後端：VM 上的小服務，透過公司內網 SMTP relay 或系統寄件帳號寄信，不必對外網開放寄信。
- 對照表：放在 VM 後端（檔案或資料庫皆可），不放進前端；前端只送暱稱或預約 id，由後端換成信箱，信箱名單不會出現在瀏覽器。
  若資料庫仍用 Supabase 且要建新表，依 `CLAUDE.md`「新建資料表要另下 GRANT」，只給 `service_role`、不給 `anon`，SQL 由使用者執行。
- 防濫用：後端只收「預約 id」，自己從 `bookings` 讀出時間、會議室、與會者再寄，不接受前端傳來的收件人或信件內容；
  同一筆預約的同一種通知只寄一次（例：記錄已寄狀態），避免被拿來對同事大量發信。

## 待 IT 確認（搬 VM 時一起問）

1. 公司信箱是 Microsoft 365 還是自架 Exchange？→ **自架 Exchange**（使用者 2026-11-02）；寄法 C（Microsoft Graph）不適用，B 走內網 SMTP relay 或系統寄件帳號。
2. 能否開一個系統寄件帳號（例：`meeting-room@gamasys.com.tw`），或允許 VM 透過內網 SMTP relay 寄信？
3. VM 的規格、網址、誰管理、還原點怎麼做（同事提議搬 VM 的理由之一是能建還原點）。

## 分期草案

1. 對照表：暱稱 → 帳號，使用者確認；不需要 IT。
2. 單次預約寄邀請：表單加勾選「寄會議邀請給與會者」；資料庫寫入成功後才寄；寄信失敗不影響預約、也不假裝成功，提示「預約成功，但邀請信寄送失敗」。
3. 修改／取消同步：改時間寄更新邀請（同一個 UID、`SEQUENCE` 遞增），刪除寄 `METHOD:CANCEL`。
4. 週期預約：一封帶 `RRULE` 的邀請取代每次一封，並處理「只改其中幾次」。
